# 智能排班系统

一个**零第三方依赖**（纯 Python 标准库 + SQLite）的本地排班与考勤统计系统，面向小团队的值班/排班场景。启动后自动打开浏览器，在网页上完成名单、人员、权限、排班任务、自动排班、考勤录入、顶班、统计全流程。

- 技术栈：Python 3.12+、`http.server`（手写 REST）、`sqlite3`、原生 HTML/CSS/JS
- 运行形态：源码运行 / 单文件 `pyz` /（麒麟）PyInstaller 单文件可执行
- 数据存储：同目录 `data.db`（SQLite，单文件，便于备份拷贝）

## 一、需求文档

### 1.1 背景与目标

团队存在多类值班/排班任务（如「日常值班排班」「机动支援排班」），需要：

1. 按**名单**维护人员，人员具备不同**权限**（消防/电工/急救/驾驶/厨师）与所属**类别**；
2. 系统**自动排班**，并保证**公平**（长期人均工作量均衡）、满足权限与在岗约束；
3. 支持**手工调整**班次、**顶班**（他人替补）与**撤销**；
4. 记录**请假/不在岗/其他考勤事件**，并在统计中按**加权分数**体现；
5. 提供**统计**：按排班表（任务）分区，展示每人的班次数与分数明细与合计；
6. 所有配置（权限、类别、考勤类型）与业务数据**持久化到数据库，不因重启/升级丢失**。

**目标**：一个离线可用、免安装、单文件即可部署、数据可整体拷贝迁移的排班系统。

### 1.2 术语

| 术语 | 含义 |
|---|---|
| 名单（roster） | 一组人员的集合，一个排班任务绑定一个名单 |
| 人员（person） | 属于某个名单，拥有多个权限、一个可选首选权限、一个类别 |
| 权限（permission） | 如 消防、电工、急救…；岗位可要求**多个**权限，人员需**全部满足**才能上该岗 |
| 类别（category） | 一组默认权限（如「管理岗」=全部技能），可快速给人员套用 |
| 任务/排班表（task） | 一个排班表就是一个任务，绑定一个名单，含若干**班次时段** |
| 班次时段（slot） | 如「早班 08:00-16:00」，一个任务内可有多个时段 |
| 岗位（position） | 班次内的具体岗位，可要求**多个权限**（需全部满足；为空=不限） |
| 排班（schedule） | 某天某岗位安排某人 |
| 考勤类型（att_kind） | 正常 / 事假 / 病假 / 缺勤 等，含**权重**与**是否不在岗** |
| 考勤记录（attendance） | 某人某天的考勤类型与事由 |
| 顶班（cover） | 让一人替代原本排班的人上某一岗位 |
| 分数/权重 | 一年内按考勤类型权重累计的工作量分值 |

### 1.3 功能需求

标记：`[已实现]`

#### FR-1 名单管理
- 新建/重命名/删除名单；删除时需明确对下属人员的处理。
- 名单用于给排班任务提供候选人员集。

#### FR-2 人员管理
- 在名单下新建/编辑/删除人员，字段：姓名、工号、电话、备注、**权限集合**、**首选权限**、**类别**。
- 选择「类别」时可一键套用该类别默认权限与首选权限；也可逐项自定义。
- 人员的权限决定其可被排到哪些岗位。
- **删除采用软删除（停用）**：仅将人员置为 `status='disabled'` 并记录 `deleted_at`，**不删除**其历史排班与考勤记录；停用者不再出现在排班候选（`load_roster`）中，可随时**恢复**。
- 人员页提供「显示已停用」开关（持久化于设置 `show_disabled`），可查看并恢复停用人员；列表对停用者标灰并显示「已停用」标签。

#### FR-3 权限管理
- 新增/重命名/删除权限（默认 消防/电工/急救/驾驶/厨师）。
- 删除权限时**级联清理**：引用该权限的人员 `perm_ids/preferred_perm_id`、类别 `perm_ids`、岗位 `perm_id`。
- 权限顺序可用（`sort`）影响展示与默认类别组合。

#### FR-4 人员类别管理
- 维护类别：名称、包含的权限集合、默认首选权限（默认 管理岗/技术岗/操作岗/辅助岗/见习岗/外包岗）。
- 人员选择类别后自动带出权限；类别可改名与调整权限组合。
- 注：当前类别的「新增/删除」未开放接口，仅支持编辑现有类别。

#### FR-5 排班任务
- 新建任务：名称 + 所属名单。
- 为任务配置**多个班次时段**（起止时间）与每个时段的**岗位**（岗位名 + 点「＋权限」弹窗勾选**多个权限**，人员需**全部满足**才能胜任该岗；已选权限以标签展示，权限多时不占版面）。
- 一个排班表 = 一个任务。

#### FR-6 自动排班
- 按月生成：`生成(year, month)`，覆盖该月该任务的排班。
- **增量重排（可选）**：`生成(year, month, start_date)`，当 `start_date` 落在该月内时，**只重排 `start_date` 至月末**的排班，`start_date` 之前的排班**原样保留**；已排段会作为公平性基准（每人已排次数预填），使新增/减少人员后该日之后的排班重新均分。不传 `start_date` 时为整月覆盖（行为不变）。`start_date` 若不在该月内则报错。
- 约束与优先级见 [1.4 业务规则](#14-业务规则与约束不变量)。
- 生成结果附带 `warnings`（如某天某岗位无人可排），供人工干预；增量模式下另返回 `incremental=true` 与 `kept_days`（保留天数）。

#### FR-7 手工调整排班
- 在排班网格中把某人指派到某天某岗位。
- 同任务内：从原岗位**移动**到目标岗位（一人一天一岗）；跨任务：时间重叠拦截，不重叠则按 `multi_shift` 放行。
- 调整时**已排人员仍可作为候选项**，但需保留「已经排过」的提示。

#### FR-8 考勤 / 不在岗录入
- 单条录入：某人某天某考勤类型 + 事由。
- **起止日期批量录入**：某人从 X 号到 Y 号不在，类型与事由一次录入，逐日写入。
- 考勤类型为「不在岗」时，该人在对应日期不参与自动排班。

#### FR-9 顶班
- **建议候选**：列出名单中**全部**有权限人员（不只未排班的），标注该人当天的已排情况与分数。
- 建议规则：在「合格（有权限、未在同岗位冲突）」的候选中，取 `(年度总分, 人员ID)` 最小者作为**建议人员**。
- 应用顶班：被顶岗位原排班者记为被顶；顶班者在**同任务内自动移入**本岗位；跨任务仍按「每人每天一班」拦截（提示 `该人员当天已在其他任务排班`）。
- 允许选择**当天已排人员**或**昨天上过同一班次的人**（连续两天同班次放宽为软偏好，不再硬拦）。
- **撤销顶班**：恢复原排班。

#### FR-10 统计
- 一级分区 = **排班表（任务）**；组内 = 该排班表所用名单的**全部人员**（含 0 班次者）。
- 未参与任何排班的人员归入「未参与排班」分组。
- 组头显示：`排班表：任务名 · 名单：名单名（N 人）`。
- 每人明细：各考勤类型计数、**总班次**、**总分数**（按该任务/人员分开累计）。
- 小计按排班表汇总；全员合计计**唯一人数**与排班表数。
- 分区与考勤分组支持**折叠**，且折叠状态需**持久**（重渲染后不丢失）。
- 时间维度：可按**年份**查看（当前年 / 前两年 / 全部）；选定年份后还可按**月份**查看（1–12 月 / **全部月份**）。
  - 「全部月份」= 整个所选年份（与旧的年维度一致）；「全部（年份）」= 历年合计，此时月份选择禁用（方案 A）。

#### FR-11 考勤类型配置
- 在「设置」页可视化增删改考勤类型：名称(label)、权重(weight)、是否不在岗(unavailable)。
- `normal`（正常）行锁定，不可删除。
- 保存即生效并持久化；排班、统计、顶班均实时读取最新配置。

#### FR-12 数据持久化与备份
- 权限、类别、考勤类型、名单、人员、任务、排班、考勤**全部落库**。
- 启动初始化幂等（`CREATE TABLE IF NOT EXISTS` + 仅空表写默认值），**重启/升级不覆盖已有配置**。
- 详见 [六、数据安全与备份](#六数据安全与备份)。

#### FR-13 排班规则设置（可配置）
- 「设置」页提供「排班规则」开关：**允许多班次**（设置键 `multi_shift`）。
- **开启（默认）**：允许同一人当天在不同任务（排班表）承担**时间不重叠**的多段班次（如 A表 12:00-14:00 + B表 14:00-16:00）；**时间重叠仍拦截**；**同一任务内仍为「一人一岗」**。
- **关闭**：**每人每天最多一班**，跨任务/跨时段均拦截（原 `busy_any` 语义）。
- **开启**：允许同一人当天在不同任务（排班表）承担**时间不重叠**的多段班次；**同一任务内仍保持「一人一岗」的移动语义**（在排班网格内调整是“移动”而非新增）。
- **时间重叠始终拦截**（与开关无关）：同一人时间上冲突的时段不可同时排。
- **同任务不连续两天排同一班次**（设置键 `avoid_repeat_slot`，**默认 `1`＝开启**）：开启时，自动排班与手工指派都会拦「昨天上过同一时段的人今天再上同一时段」；关闭后允许连着上同一班次。
- **顶班允许一人一天多班**（设置键 `cover_multi_shift`，默认 `0`）：**仅影响顶班**。开启后顶班人无需让出自己当天的班，可同时保留原班并接手被顶班次（**时间不重叠**，重叠仍拦截）。**不改变自动排班算法**（仍以均匀分配为主）。
- 开关值持久化于 `settings` 表，通过 `/api/settings` 读写；排班生成与手工指派、顶班实时读取最新值。

#### FR-14 数据自检
- 「设置」页提供「数据自检」按钮，调用 `GET /api/selfcheck`。
- 检查项：孤立引用（记录指向已删除对象）、跨任务同日冲突（**仅当多班次关闭时**计入问题）、时间区间重叠、同一岗位同日多条底班、顶班指向不存在的底班、非法考勤类型、权限引用失效。
- 返回 `{ok, issues, settings, checks, counts}`；开启多班次后，正常的跨任务同日排班降级为信息项，不再计入 `issues`。
- 「**一键修复悬空顶班**」按钮调用 `POST /api/selfcheck/repair`：对「`cover_of` 找不到底班」的孤立顶班行，若该岗位当天已有其它底班则删除，否则**升为底班**。
- 约定：`cover_of` 存的是**被顶人的 `person_id`**（不是排班行 id）。

### 1.4 业务规则与约束（不变量）

排班/顶班必须满足：

1. **每人每天最多一班**：同一任务内恒定。当「允许多班次」（`multi_shift`）**开启（默认）**时，放宽为「**跨任务间时间不重叠即可**」；**关闭**时跨任务也拦截。无论开关如何，**时间重叠始终拦截**，且同一任务内始终「一人一岗」（见 [FR-13](#fr-13-排班规则设置可配置)）。
2. **岗位权限匹配**：人员权限须包含岗位要求的权限（岗位权限为空=不限）。
3. **不在岗不排班**：考勤类型 `unavailable=1` 的人员当天不参与排班。
4. **同任务不连续两天同一班次**：昨天上过的班次，今天不排（自动排班为硬约束；顶班时放宽为软偏好）。**可在「排班规则」关闭**（设置键 `avoid_repeat_slot`，默认开启）。
5. **公平性**：候选排序键（越小越优先）：
   `本月已排次数 → 本时段已排次数 → 偏好匹配 → 年度总分 → 人员ID`
   - 本月已排次数为主键，保证同月内人人均分；
   - 本时段已排次数为次键，保证同一人在**各时段间**也尽量均分（避免某人总上夜班 / 从不上早班）；
   - 年度总分（按权重累计）为后续键，保证跨月/跨年公平；
   - 岗位按**权限可选人数**从少到多处理，优先满足权限受限岗位；相同可选人数时按日期**轮换时段优先序**，使人手不足时「空档时段」逐日轮换、所有时段长期都有覆盖。
6. **年度分数**：按考勤类型权重累计，权重可由「设置」页配置（默认：正常 1.0 / 事假 0.8 / 病假 0.5 / 缺勤 0）。

### 1.5 非功能需求

- **NFR-1 依赖**：仅使用 Python 标准库，无 pip 依赖（`dependencies = []`）。
- **NFR-2 离线**：完全本地运行，绑定 `127.0.0.1`，不联网。
- **NFR-3 部署**：支持单文件 `pyz` 与（麒麟）PyInstaller 单文件；双击/脚本启动。
- **NFR-4 可迁移**：数据集中在单个 `data.db`，拷贝即迁移。
- **NFR-5 兼容**：Python ≥ 3.12；适配麒麟等国产 Linux。
- **NFR-6 可测试**：提供 `selftest.py` 与 E2E 脚本。
- **NFR-7 免缓存**：静态资源 `Cache-Control: no-store`，避免升级后浏览器读到旧页面。
- **NFR-8 端口**：默认 `8686`，可用环境变量 `WORKDAY_PORT` 覆盖；端口被占用时视为「已在运行」并打开浏览器。
- **NFR-9 移动端**：窄屏（≤820px / ≤480px）自适应——顶栏导航换行、双栏变单列、列表表格在卡片内横向滚动、排班表纵向滚动；手机浏览器可直接使用。

## 二、数据模型

单文件 SQLite（`data.db`），核心表：

| 表 | 关键字段 | 说明 |
|---|---|---|
| `permissions` | `id, name, sort` | 权限字典（默认 消防/电工/急救/驾驶/厨师） |
| `categories` | `id, name, perm_ids(JSON), preferred_perm_id` | 人员类别与默认权限（默认 管理岗~外包岗） |
| `rosters` | `id, name` | 名单 |
| `persons` | `id, roster_id, name, code, phone, category_id, perm_ids(JSON), preferred_perm_id, remark, status, deleted_at` | 人员；`status`=`active`/`disabled`（软删除），`deleted_at` 记录停用时间 |
| `tasks` | `id, name, roster_id` | 排班任务（=排班表） |
| `slots` | `id, task_id, idx, start, "end"` | 班次时段 |
| `positions` | `id, slot_id, name, perm_id, perm_ids(JSON)` | 岗位要求的权限集合（`perm_ids` 为准，需全部满足；`perm_id` 为兼容镜像=首个） |
| `schedules` | `id, task_id, date, slot_id, position_id, person_id, cover_of`，`UNIQUE(task_id,date,position_id,person_id)` | 排班记录；`cover_of` 指向被顶班者 |
| `attendance` | `id, person_id, date, kind, reason`，`UNIQUE(person_id,date)` | 考勤记录 |
| `att_kinds` | `kind(PK), label, weight, unavailable, sort` | 考勤类型配置（运行期唯一来源） |
| `settings` | `key(PK), value` | 全局设置键值对（`multi_shift`、`show_disabled`、`cover_multi_shift`、`avoid_repeat_slot`） |

**索引**（加速按日期/人员/岗位查询）：`schedules` 上 `date`、`(person_id,date)`、`(task_id,date)`、`slot_id`、`position_id`、`(date,position_id)`；`attendance` 上 `date`、`(person_id,date)`；`persons(roster_id)`、`persons(status)`、`slots(task_id)`、`positions(slot_id)`。

**说明**
- `perm_ids` 以 JSON 字符串存储（如 `[1,2,3]`）。
- `att_kinds` 是「考勤类型」的唯一运行期来源，`normal` 恒存在。
- `settings` 用于运行期可调规则（`multi_shift`：允许多班次，默认 `1`；`show_disabled`：人员列表是否显示已停用者，默认 `0`；`cover_multi_shift`：顶班允许一人一天多班，默认 `0`；`avoid_repeat_slot`：同任务不连续两天同班次，默认 `1`）；启动时仅补默认键，不覆盖已有值。
- `persons.status` 为软删除标记；旧库在启动时由 `_migrate_persons_soft_delete` **幂等补列**（自动 `ALTER TABLE`），无需手工迁移。
- 旧库中占位的权限（`A~E`）与类别（`一类~六类`）会在启动时由 `_migrate_rename_placeholders` **幂等改名**为真实名称（消防/电工/急救/驾驶/厨师、管理岗~外包岗）；若目标名称已存在则跳过，不会产生重名。
- 考勤类型占位名 `A事/B事` 由 `_migrate_att_kind_labels` 在启动时**幂等改名**为 `事假/病假`（仅当旧名存在）。
- 数据库以 **WAL 模式**运行（`PRAGMA journal_mode=WAL`），提升多写并发；连接设 `busy_timeout=5000`、`synchronous=NORMAL`。
- 无外键约束，删除时由应用层手工级联清理。

## 三、API 一览

REST，JSON 收发。基址 `http://127.0.0.1:8686`。

## 六、数据安全与备份

### 结论：权限等配置数据均在数据库（`data.db`）中，重启/升级不会丢失

| 页面 | 落库表 | 接口 |
|---|---|---|
| 权限列表 | `permissions` | GET/POST/PUT/DELETE `/api/permissions` |
| 人员类别与默认权限 | `categories` | GET `/api/categories`、PUT `/api/categories/{id}` |
| 考勤类型 | `att_kinds` | GET/POST/PUT `/api/att_kinds` |
| 排班规则（允许多班次） | `settings` | GET/POST/PUT `/api/settings` |

**为什么不丢**
1. 每次请求实时查表，不存在「只改前端内存」。
2. 启动 `init_db()` 使用 `CREATE TABLE IF NOT EXISTS`，且种子数据**仅在表为空时**写入 → 重启/升级不覆盖已有配置。
3. 写入即 `commit()`，SQLite 事务保证落盘。

**注意事项**
1. **数据库文件位置**：
   - 源码运行 → 读**脚本同目录** `data.db`
   - pyz 运行 → 读 **pyz 同目录** `dist/data.db`
   - 两者是**两个不同的库**；**迁移/分发时务必把 `data.db` 与程序一起拷贝**，否则目标机会新建空库（默认 消防/电工/急救/驾驶/厨师）。
2. `seed_demo.py --force` 会清空业务数据（配置不受影响）——勿在生产库执行。
3. 边界：若把所有权限删光，下次启动会因表为空**重新写入默认权限（消防/电工/急救/驾驶/厨师）**。
4. 目前无自动备份/导出功能，建议**定期手工备份 `data.db`**。

**备份建议**：停止服务后直接复制 `data.db`（如 `cp data.db data.db.bak`）即可。

### 配置看起来「重启就丢了」怎么办

配置本身是**持久化**的（存在 `data.db` 里）。若重启后配置变了，几乎都是**读到了另一个 `data.db`**：

1. **看启动日志 / 设置页**：启动时会打印 `数据文件: /绝对路径/data.db`；「设置」页底部也有「数据文件」卡片显示当前库路径。
   - 若该路径**每次启动都不一样**，或每次都提示「首次创建」，就说明程序位置/运行目录在变。
2. **三种运行方式的数据文件位置不同**：
   - 源码 `python3 server.py` → 脚本同目录 `./data.db`
   - pyz `python3 排班系统.pyz` → **pyz 同目录** `data.db`
   - 可执行 `./排班系统` → **可执行文件同目录** `data.db`
   - 从**不同位置/方式**启动会各用各的库 → 配置看起来「丢了」。**固定从同一处启动**即可。
3. 换新版本时，**把旧的 `data.db` 一起带过去**（放到程序同目录）。
4. 不要把程序放在重启会被清空的目录（如某些临时目录）。

## 八、适用团队规模与扩展性

### 8.1 推荐团队规模

**最适合 10–50 人的团队**（单个部署实例）。50–100 人仍很流畅；**100–200 人**是「能用但开始有感知延迟」的区间；**200 人以上**建议优化或按需拆分。

当前测试数据为 16 人 / 2 个排班表，远低于实用瓶颈。

### 8.2 瓶颈分析

**1. 数据量**
- 排班行数 ≈ 人数 × 当月天数（每人每天最多一班）。
- 实测：16 人 → ~311 行/月。推算：50 人 ~1000 行/月（~1.2 万行/年）、100 人 ~2000 行/月（~2.4 万行/年）、200 人 ~5000 行/月（~6 万行/年）。
- SQLite 单文件能轻松承载百万行，**存储本身不是限制**。

**2. 后端算法**
- `generate_month` 按天贪心计算（天数 × 岗位 × 候选人数），100 人一个月约万级比较，毫秒级。
- `year_scores`/`get_stats` 在内存中聚合当年排班与考勤数据，百人级别的数据量很小。

**3. 曾经的瓶颈：全部年份统计 + 前端整表渲染（已优化）**
- `get_stats` 为每个 **（排班表 × 人员）** 组合生成一行（各考勤类型计数 + `总班次` + `总分数`）。
- **已优化**：移除了每行的 `scores` 明细数组（前端从不使用），响应体积大幅下降（16 人测试库 `全部年份` JSON ≈ 3KB）；前端统计改为**分组懒渲染**——行数 > 300 时默认折叠，分组明细**首次展开时才插入 DOM**（实测 320 行时首屏 DOM 内明细行数 = 0）。
- 剩余影响：选择「全部年份」且分组被**全部展开**后，仍是整组渲染，暂无虚拟滚动。

**4. 并发能力**
- 单进程 `ThreadingHTTPServer`，每次请求新建 SQLite 连接（无连接池），静态资源 `Cache-Control: no-store`。
- SQLite 已启用 **WAL**（`journal_mode=WAL`）并设 `busy_timeout=5000`、`synchronous=NORMAL`，多写并发与抗锁能力显著改善。
- 系统无登录/权限分级与并发编辑冲突检测（采用后写覆盖）。
- **推荐**：同时在线编辑 **2–5 人** 没问题；适合作为「少数人共用的本地后台工具」，不适合作为高并发 Web 服务。

**5. 前端渲染规模**
- 单页应用，名单、人员、排班网格、统计均为整表渲染，**无虚拟滚动**；其中**统计已支持分组懒渲染**（大表默认折叠、按需插入），其余列表在数百行时 DOM 仍会变重。

### 8.3 分档建议

| 团队规模（总人数） | 体验 | 建议 |
|---|---|---|
| ≤ 50 人 | ✅ 最合适 | 充分发挥多权限、多班次、公平性等复杂规则优势 |
| 50–100 人 | ✅ 流畅 | 建议统计默认按年查看，避免选择「全部年份」 |
| 100–200 人 | ⚠️ 可用 | 全部年份统计 + 整表渲染会有延迟；并发保存需谨慎 |
| > 200 人 | ❌ 不推荐 | 建议优化或改用其他方案 |

> 注：总人数指该部署下所有名单的总人数（多个排班表/任务会累加统计行数）。

### 8.4 优化落地情况

**本版已实施**：

| 优化点 | 说明 |
|---|---|
| 统计移除 `scores` 明细数组 | 响应体积大幅下降；前端本就不使用该字段（**API 变更**） |
| 统计分组懒渲染 | 行数 > 300 默认折叠，展开时才把该组明细插入 DOM |

**后续可选（按性价比）**：

|---|---|---|---|

排班算法实现分析（核心：按日贪心 + 多维排序 + “先难后易”岗位处理）

1. 概览
- 入口：generate_month(task_id, year, month)（覆盖该月该任务的排班，先 DELETE 再重排）
- 每天：_generate_day(...) 执行贪心分配
- 公平性依赖：gen_count（本月已排次数）、slot_count（每人各时段已排次数）、year_scores（年度累计权重）、偏好匹配（preferred_perm_id==position.perm_id）、岗位“权限可选人数”优先

2. 核心数据准备（每天）
- yslots = _yesterday_slots(task,date-1) → 昨天同任务各人的班次（用于“不得连续两天同班次”硬约束）
- scores = year_scores(year) → 每人年度各考勤类型计数和 total（权重累计）
- busy_today = 当天全库已有排班的 person_id（跨任务“每人每天最多一班”）
- available = 名单中非不在岗（attendance.kind 在 att_kinds 中 unavailable=True 则不排）
- assigned = 当天本任务已分配的 person_id
- gen_count / slot_count 由保留段预填（整月重排=0；增量重排=start_date 之前的已排）

3. 时段均衡（替代旧的 rotation_rank）
- 次键用 slot_count[(pid, sid)]：优先把该人排到“他做得最少”的时段
- 目标：同一人在各时段间尽量均分（避免某人总上夜班、有人从不上早班）

4. 合格条件 eligible(p, sid, pos)
- 权限不符：_perm_ok → 岗位 perm_id 为空放行，否则人员 perm_ids 必须包含
- 同任务一人一天一岗：pid in assigned 或 昨天同班次 yslots.get(pid)==sid → False
- 多班次开启：跨任务仅“时间重叠”才拦截；关闭：当天全库已有排班即拦截

5. 候选排序键 key(p, sid, pos)（tuple，越小越优先）
- gen_count[p.id]（本月已排次数）→ 主键：人人均分
- slot_count[(p.id, sid)]（本时段已排次数）→ 次键：时段均衡
- match：preferred_perm_id==position.perm_id ? 0 : 1（首选权限匹配）
- person_total(scores, p.id)（年度总分）→ 跨月公平
- p.id（稳定破平）

6. 岗位处理顺序（“先难后易” + 缺人轮换）
- jobs = [(n, sid, pos)]，n = sum(1 for p in available if _perm_ok(p,pos))（**按权限**的稀缺度）
- jobs.sort(key=(n, slot_prio[sid], sid))：权限可选人数最少的最先分配；相同则按“随日期轮换”的时段优先序 slot_prio
- 用意：① 优先满足“稀缺权限”岗位，避免被普通岗位抢占唯一合格人选；② 人手不足时“空档时段”逐日轮换，所有时段长期都有覆盖

7. 单岗位分配
- cands = sorted(eligible, key=key) → 取 cands[0] 分配
- assigned.add(pid)、gen_count[pid]+=1、slot_count[(pid,sid)]+=1、写入 schedules（cover_of=None）
- 若 cands 为空 → 记录 warning（“XX XX:XX-XX 岗位「Y」无人可排”）

8. 顶班（简述）
- suggest_covers：名单内具备权限、非不在岗；计算 busy（当天全库是否有排班）、risky（昨天是否上过同一 slot）；eligible = not busy and not risky；若有 eligible，选 (total, person_id) 最小者标 suggested；排序（suggested→eligible→total→id）
- apply_cover：找到岗位原排班（cover_of IS NULL），校验不在岗/权限/跨任务拦截（跨任务若已有排班报错），同任务内允许当天已排人员 → 删除该人当日同任务排班再插入新顶班行（cover_of=base_pid）

9. 公平性要点
- 本月均分（gen_count 主键）+ 时段均衡（slot_count 次键）+ 年度权重均衡（year_scores total）
- 候选集是“全体可用人员”（不是“曾经排过的人”）
- 岗位按“权限可选人数”升序（先难后易）+ 同稀缺度按日期轮换，减少“卡死”与“固定空岗”
